Ball Party · layout study

Layout C — the slim top bar

The web-platform model. A persistent bar carries identity and the join code on every page, and the home screen is a game grid. This is the Jackbox / skribbl shape: a code from a friend works from wherever you already are, and a stranger who lands on / sees the actual games rather than copy about them.

Same page for signed-out and signed-in — the actions are gated, not the screen. Both states are shown below so the delta is visible.

The one rule this layout has to respect: the bar is background, never panel. Panels are the only light surface in the product, so chrome that isn't a panel stays dark — which is also why the join field reads as an inset well rather than a control on a panel.

A first-time visitor at /. The bar still offers the join field, because the most likely reason a stranger is here is that someone read them a code out loud. Primary CTA is the table; the grid below is the pitch.

03 — Mobile · where this layout is weakest, and how it survives

The nav links collapse behind a burger; the join field never does — it is the one control worth its width on a 390px screen. Game cards drop their description and go two up. This is the honest cost of C: on a phone the bar spends 52px on chrome that Layout A spends on the table.

What this mockup commits to

The join field lives in the bar, not on the home page

This is the whole reason to pick C over A. A code arrives by text while you're mid-solo-game or reading a game's rules page, and it works from there. It also means the home hero doesn't have to carry two competing primary actions — home is start, the bar is join.

Signed-out is the same page with dead CTAs

Compare frames 01 and 02: identical grid, identical bar, identical section order. The delta is the hero-vs-strip swap and Sign in in place of Play solo / Start a room. One route, one component tree, one set of styles to keep honest. A separate marketing page would double all three for a product with three games.

The grid is a shop window, not the play surface

Three of four games need four people, so their card CTA is Start a room — it creates a room seeded with that game, it does not start a match. Real game selection still happens inside the room at "Start a run", exactly as lobbies.md specifies. Only Higher or lower gets a true Play solo, because it's the only one that means anything alone. If you ever add a game that reads as playable solo but isn't, this grid starts lying.

Unbuilt games are concealed, not greyed out

The fourth tile carries the red weave rather than a greyed-out ghost card. Red means not yet revealed everywhere else in the product, so it should mean that here too. It also makes a thin catalogue look deliberate rather than unfinished.

What C costs you

52px of permanent chrome on a phone, a burger menu you now have to design and test, and a home screen that leads with browsing when the product's real first move is making a room. If the analytics come back saying almost nobody touches the nav links, that's the signal to fall back to Layout A and keep only the bar's join field.

Not shown, and worth deciding next

Signed-out /lobby/[code] — the page most new users will actually land on. It should render the room (names, players in, spots left) with sign-in as the single action, and proxy.ts currently redirects it to /login instead.
